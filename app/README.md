## Требования

Проверено на Elixir 1.19.5 / Erlang OTP 28, PostgreSQL 18.6. Версии в `.tool-versions`,
зависимости зафиксированы в `mix.lock`. Нужны инструменты C-сборки для bcrypt и доступ
к Hex при первой установке. JS собирает esbuild, Node/npm-проект не нужен.

## Повторяемая локальная проверка первого этапа

Из `app/`, после установки зависимостей:

```sh
bash dev/check_queue1_local.sh
```

Не загружайте `.env` для этого прогона. Нужны PostgreSQL 18 (по умолчанию
`/usr/lib/postgresql/18/bin`), Elixir/Mix, Node для существующих JS-тестов
и OpenSSL для одноразового пароля тестовой базы. При необходимости задайте
`QUEUE1_PG_BINDIR` и свободный `QUEUE1_CHECK_PORT` (по умолчанию 59433).
База создаётся только в новом каталоге `/tmp/anime-queue1-check.XXXXXXXX`;
переданные URL базы игнорируются. TCP — только loopback с SCRAM-паролем,
сайт и внешние почта/MinIO не запускаются.

Полный откат касается только этой временной базы. Скрипт останавливает свой
сервер даже при ошибке; сохраняет базу, отдельные логи этапов, снимки схемы и
HTML-покрытие. Путь печатается в конце. Ошибка любого обязательного локального
шага возвращает ненулевой код. Пакетные аудиты могут требовать доступ к реестрам.
Проверяются общий порог строк 80%, каждый модуль контекста 90%, Oban-воркер 85%,
прикладной plug и проверка разрешений 100%. Шаблоны HEEx исключаются отдельно
от логики тех же модулей. Правила/исключения и реальный остаток CI описаны в
[контрольном списке](../keep/queue1-acceptance.md). Основные отчёты —
`cover/coverage.json` и `cover/coverage.txt`; HTML Mix остаётся исходным, без фильтрации.
Шесть изолированных проверок `dev/coverage_gate_smoke.exs` проверяют коды отказа.
Скрипт не объявляет первую очередь завершённой и не включает staging/prod.

Заготовка задания CI: `bash dev/check_queue1_ci.sh --help`. Нужны чистый
Git-коммит, установленный инструментарий и доверенный JSON основной ветки:
`QUEUE1_BASE_COVERAGE` плюс `QUEUE1_BASE_REVISION`. Настоящего CI пока нет;
без базового отчёта локальный прогон явно не проверяет допустимое падение покрытия.
`assets.deploy` здесь собирает локальные минифицированные ресурсы и manifest;
не загружает файлы на сервер и не запускает приложение.

## Локальный запуск

### Проверка самостоятельного пакета

```sh
bash dev/check_release_local.sh
```

Это подготовка release, **не запуск сайта и не разрешение production**.
Команда компилирует `MIX_ENV=prod`, собирает ресурсы и новый пакет `anime`
со встроенным ERTS в `/tmp/anime-release-check.XXXXXXXX/package`.
Существующие пакеты не перезаписываются. Зависимости должны быть установлены;
скрипт не читает `.env`, не применяет миграции и не создаёт пользователей.

Проверяется комплект ресурсов/шрифтов/миграций, отсутствие dev/test-зависимостей,
исходного дерева приложения, корневых .env/deps/_build и тестовых fixtures.
Затем пакет выполняет `eval` из `/tmp` с PATH без установленного Elixir/Mix:
читает синтетическую конфигурацию, загружает bcrypt NIF, проверяет безопасные отказы.
Anime, Repo и Endpoint не запускаются. Файлы пакета до/после должны совпадать.

В пакет включён `bin/server`: устанавливает PHX_SERVER=true и через exec
передаёт управление соседнему bin/anime start. Путь с пробелами и отказ на
посторонние аргументы проверяются на фиктивном соседнем executable, не на живом сайте.

Для команд релиза обязательны внешние `RELEASE_COOKIE` (не менее 32 символов)
и `RELEASE_TMP` — существующий writable-каталог вне пакета. Используйте приватный
каталог владельца процесса: там могут сохраняться runtime-настройки с секретами.
В проверке это новый каталог с правами 700; значения только синтетические.
Встроенный COOKIE — публичная заглушка, не рабочий секрет. Distributed Erlang
пока запрещён; разрешён только RELEASE_DISTRIBUTION=none. APP_ENV=staging/prod,
NODE_ROLE=media и SMTP по-прежнему отклоняются существующей конфигурацией.

Локальный запуск release с отдельной БД и /healthz, команды migrate/rollback/seed
проверяются отдельным runner ниже. storage_setup также проверен на отдельном MinIO
через dev/check_storage_local.sh; детали и ограничения — deploy/STORAGE_SETUP.md.
Не выполнены: реальное provisioning хранилища, контейнер, TLS-прокси,
внешние SMTP/MinIO и staging. Не направляйте пакет на рабочую базу.
Полный build-check добавлен в заготовку check_queue1_ci.sh, но удалённого CI ещё нет.

### Миграции из собранного пакета

В отдельном процессе, с внешними runtime-настройками из раздела выше:

```sh
bin/anime eval 'Anime.Release.migrate()'
bin/anime eval 'Anime.Release.rollback(Anime.Repo, 0)'
```

Вторая команда откатывает **все** миграции и может удалить данные. Вместо 0
можно передать целевую версию, которая остаётся применённой (откатываются более
новые версии); не запускать на рабочей базе без отдельного решения.
Обе команды требуют `MIGRATION_DATABASE_URL`, без подстановки `DATABASE_URL`.
Они не запускают приложение, Endpoint, Oban или seed; используется отдельный
репозиторий миграций с lock_timeout 5с, statement_timeout 0 и advisory lock.
Запуск поверх уже работающих Anime/Repo запрещён. Настройки отдельного
репозитория восстанавливаются после вызова; его соединения закрываются.
Ограничения dev/web и запрет staging/prod остаются в силе.

Безопасное повторение проверки на **новой временной базе**:

```sh
bash dev/check_release_database.sh /tmp/anime-release-check.XXXXXXXX/package
```

Укажите пакет, полученный предыдущим runner. Скрипт не читает `.env`, создаёт
свой PostgreSQL 18 на 127.0.0.1:59434 и останавливает его при выходе.
Роль миграций владеет только тестовой базой, без SUPERUSER/CREATEDB/CREATEROLE.
Проверяется отсутствие запасного подключения, 47 миграций вверх, повтор без
изменений, полный откат и повторное применение с одинаковой схемой.
Результат 1 октября: `/tmp/anime-release-db.XzI5HRUr`, exit 0;
пакет `/tmp/anime-release-check.SDQ4E65B`.
Этот предыдущий прогон проверял только миграции. Теперь runner дополнительно

### Начальное заполнение и тестовый запуск сборки

```sh
bin/anime eval 'Anime.Release.seed()'
```

Команда использует `DATABASE_URL` обычной роли (не миграционной) и требует
внешние `ADMIN_EMAIL`, `ADMIN_NICK`, `ADMIN_PASSWORD`. Секреты не передавать
аргументами командной строки. Схема должна быть заранее установлена.
Создаются справочники и первоначальный владелец с обязательной сменой пароля;
повтор возвращает `{:ok, :already_exists}`, не меняя существующие grants.
Endpoint и Oban не запускаются; временные Repo/PubSub/Cache/Passwords останавливаются.
Запуск команды внутри работающего приложения запрещён.

`check_release_database.sh` теперь проверяет также seed дважды, сохранность
записей и отозванного права, затем запускает bin/server на свободных loopback
портах 49137/49568. Рабочие порты не затрагиваются. Обычная роль имеет DML
к существующим таблицам, но не CREATE и не SUPERUSER/CREATEDB/CREATEROLE.
Для проверки HTTPS-перенаправления в локальном HTTP запросе передаётся
X-Forwarded-Proto: https; это не тест настоящего TLS-прокси.
MinIO намеренно недоступен; /readyz должен вернуть только storage в failed.
При выходе отправляется SIGTERM собственному процессу, проверяется запись
Application stopped и останавливается свой PostgreSQL. Каталог доказательств
сохраняется с правами 700; в нём только синтетические тестовые данные.

### Запуск разработки

1. Запустите отдельный PostgreSQL для разработки, не используйте рабочую базу.
2. Скопируйте `.env.example` в `.env`. Задайте URL базы, два независимых случайных
   секрета, параметры MinIO. `.env` исключён из Git; приложение само этот файл не читает.
   Порт 59432 в примере относится к изолированной базе текущего прогона; при своём
   PostgreSQL измените оба URL. Не передавайте реальные учётные данные сторонним сервисам.
3. Из `app/` загрузите переменные и выполните:

```sh
set -a
. ./.env
set +a
mix deps.get --check-locked
mix ecto.create
mix ecto.migrate
mix run -e 'Anime.Seeds.defaults()'
mix assets.build
node test/js/admin_table_test.mjs
node test/js/admin_shell_test.mjs
node test/js/public_header_test.mjs
mix phx.server
```

Откройте [регистрацию](http://localhost:4000/register) или [вход](http://localhost:4000/login).
Сервер слушает только `127.0.0.1`. Используйте `localhost`: сессионные cookie имеют Secure.
Письма **не уходят в интернет**: в dev используется локальный Swoosh, просмотр —
[почтовый ящик](http://localhost:4000/dev/mailbox). Проверка MX при регистрации включена;
для локального теста нужен адрес с существующим почтовым доменом. В тестах DNS отключён.

`mix setup` выполняет получение зависимостей, создание/миграции базы и сборку ресурсов,
но **не создаёт пользователя** и не заменяет явный запуск `Anime.Seeds.defaults()`.
Владелец также не создаётся автоматически. Для него отдельно задайте `ADMIN_EMAIL`,
`ADMIN_NICK`, `ADMIN_PASSWORD`, затем `mix run priv/repo/seeds.exs`. На первом входе
требуется сменить пароль. Не храните пароль владельца в shell history/общем файле.
Повторный seed сохраняет изменённую матрицу и не возвращает отозванные права.
Исходные grants добавляются новым системным ролям и новым Permission по п.17 ТЗ.

После изменений перезапустите сервер; автоматическая перезагрузка кода выключена.
После CSS/JS дополнительно выполните `mix assets.build`.

## Проверка конфигурации перед запуском

`config/runtime.exs` получает готовую типизированную конфигурацию из
`Anime.RuntimeConfig`. Для обычного запуска обязательны APP_ENV, NODE_ROLE,
PHX_HOST, SECRET_KEY_BASE, LIVE_VIEW_SIGNING_SALT, DATABASE_URL, MINIO_ENDPOINT,
MINIO_PUBLIC_URL, MINIO_ACCESS_KEY_ID и MINIO_SECRET_ACCESS_KEY.

- Сейчас разрешены только APP_ENV=dev, NODE_ROLE=web и MAIL_ADAPTER=local.
  Staging/prod, media и SMTP намеренно останавливают запуск, а не включают
  неготовую функцию или незаметно подменяют её локальным режимом.
- Секрет и salt — разные значения, минимум 64 и 32 символа соответственно.
  Обязательные пустые/пробельные значения и управляющие символы отвергаются.
  У необязательной переменной значение по умолчанию работает только при её отсутствии.
- PHX_HOST — DNS-имя (IDN в punycode) либо IPv4, без схемы/порта/пути.
  PORT — 1–65535, по умолчанию 4000; POOL_SIZE — положительное целое, по умолчанию 10.
- METRICS_PORT — 1–65535, по умолчанию 9568; совпадение с PORT — ошибка.
  Отдельный listener включается при PHX_SERVER=true, только на 127.0.0.1.
- Оба адреса MinIO — HTTP(S) origin, без учётных данных, бакета/пути, query и fragment;
  DNS, IPv4 и IPv6 в квадратных скобках допустимы. Завершающий `/` снимается.
- DATABASE_URL — ecto/postgres/postgresql с пользователем, сервером и именем базы.
  Поддерживаются только URL-опции `ssl=true/false`, положительные `timeout` и
  `idle_interval`; дубли и остальные опции отвергаются. Пул задаётся POOL_SIZE.
  DATABASE_SSL принимает true/false; при отсутствии берётся ssl из URL либо false
  для текущей локальной среды. Противоречащие значения останавливают запуск.
- PHX_SERVER — true/false, по умолчанию false; `mix phx.server` сам включает HTTP.
  LOG_LEVEL принимает debug/info/warning/error; некорректное значение — ошибка.
  Более конкретное правило п.21 фиксирует dev/test на debug, включая отсутствие
  переменной или явное info/warning/error. Изменение LOG_LEVEL не понижает этот
  порог в текущем dev-срезе. TZ — только UTC (UTC). Политика staging/prod пока
  не включена, как и сами эти окружения; файлового журнала/ротации ещё нет.

Отказ при запуске возвращает код 1 и сообщение `Invalid runtime configuration`
с именем переменной, без значения или URL с паролем. Preflight не проверяет DNS,
соединения, правильность паролей БД/MinIO и существование бакетов: доступность
зависимостей отдельно проверяет `/readyz`.

Без запуска приложения и внешних сервисов можно повторить десять синтетических
CLI-сценариев (действительную `.env` для них загружать не нужно):

```sh
mix compile --warnings-as-errors
elixir dev/runtime_preflight_smoke.exs
```

`MIX_ENV=test` использует отдельную конфигурацию test.exs, а не рабочие переменные
приложения; правило отдельной безопасной TEST_DATABASE_URL остаётся обязательным.
Полный набор production-переменных ТЗ и инфраструктурные проверки ещё не реализованы.

## Локальные метрики

При PHX_SERVER=true отдельный `http://127.0.0.1:9568/metrics` отдаёт Prometheus text.
В основном endpoint этот путь отвечает 404. Без флага накопление есть, порта нет;
если используется только `mix phx.server` без PHX_SERVER=true, включён сайт,
но не отдельный listener метрик. Порт можно изменить через METRICS_PORT.

Скрейп не требует сессии, доступен только с loopback; публично проксировать его нельзя.
Внешний Prometheus/графики и private-network bind будущего развёртывания ещё не настроены.
Счётчики живут до перезапуска reporter, не сохраняются в БД. Ненаблюдавшиеся ряды
отсутствуют. Длительности в целых микросекундах; для секунд делите на 1000000.
Примеры запросов, точные имена и открытый вопрос квантилей — в
[отчёте](../keep/queue1-metrics-exporter-check.md).

Снимок пула: `anime_db_pool_ready`, `anime_db_pool_waiting`,
`anime_db_pool_snapshot_available`. Первые два ряда выводятся только при свежем
снимке моложе 30 секунд. При отказе, остановке сборщика или устаревании остаётся
только `snapshot_available=0`; это не ложные нули соединений/очереди.
Поддерживается один обычный пул нынешнего dev/web, без SQL-запросов при опросе
и scrape. Sandbox/partitioned pool не выдаются за поддержанный физический пул.
Подробности, перезапуски и ограничения — [отчёт пула](../keep/queue1-pool-metrics-check.md).

Ресурсы: `anime_vm_memory_bytes{kind="..."}` (девять фиксированных категорий),
`anime_vm_process_count`, `anime_vm_port_count`, `anime_vm_atom_count`,
`anime_vm_gc_collections` (накопленное число GC с запуска VM, не их длительность),
`anime_application_start_time_seconds`, `anime_application_uptime_seconds`,
`anime_vm_snapshot_available`. Память в байтах, время запуска в Unix-секундах,
uptime — полные секунды по монотонным часам, измеренные при последнем опросе.
Период 15 секунд, таймаут 1 секунда, свежесть строго меньше 30 секунд.
При недоступном/просроченном снимке остаётся только availability=0, не ложные нули.
Категории памяти пересекаются; их нельзя суммировать, это не RSS всей машины.
Использовать `Anime.Metrics.Exporter.scrape/0`, а не сырой Core.scrape:
последний не умеет удалять устаревшие gauges. Источник для будущего Uptime
админки — `Anime.RuntimeClock.measure/0`, не отдельные часы в LiveView.
Правила и пределы — [отчёт ресурсов](../keep/queue1-vm-metrics-check.md).

Планировщики: `anime_scheduler_run_queue_length{kind,id}` и
`anime_scheduler_utilization_ratio{kind,id}`. Нормальные очереди отдельные,
dirty_cpu и dirty_io имеют по одной общей очереди с id=shared. Доля занятости
планировщика 0–1 считается между двумя свежими снимками, а не за всю жизнь VM;
это не процент CPU операционной системы. У выключенных планировщиков нет ряда
utilization. `anime_scheduler_snapshot_available{measurement}` отдельно сообщает
доступность queues и utilization; при первом замере queues=1, utilization=0.
Период/таймаут/свежесть — 15с/1с/<30с. Измерение scheduler_wall_time принадлежит
живому сборщику и освобождается при его завершении; чужое измерение не отключается.
Перечень kind/id замкнут числом созданных планировщиков. Проверяется весь возможный
набор, в том числе сейчас выключенные: при >500 рядах определения отклоняются,
показатели не обрезаются. Подробности — [отчёт](../keep/queue1-scheduler-metrics-check.md).

Версии: `anime_runtime_info{component,version}` — константа 1 для application,
elixir и erlang_otp. OTP отдаёт основной выпуск (например, 28), не patch 28.5.
Пары меток ограничены фактической средой и восстанавливаются при перезапуске
reporter; PostgreSQL добавлен отдельной метрикой ниже, FFmpeg ещё не реализован.

Кэш: `anime_cache_entries{table}`, `anime_cache_memory_bytes{table}` и
`anime_cache_snapshot_available{table}`. Пока только anime_role_permissions;
перечень и общий источник для будущего экрана — `Anime.Cache.inventory/0` и
`Anime.Cache.statistics/0`. Память ETS пересчитана из слов в байты, это не полный
объём разделяемых бинарных данных. Пустой кэш отличим от недоступного. Период,
timeout и freshness — 15с/1с/<30с; перезапуск и сброс отражаются при следующем
замере. Scrape не читает таблицы/SQL, содержимое кэша не экспортируется.
[Подробности и пределы](../keep/queue1-inventory-metrics-check.md).

Задачи: `anime_oban_jobs{queue,state}`,
`anime_oban_oldest_available_age_seconds{queue}` и `anime_oban_snapshot_available`.
Пока только mailers/maintenance и семь состояний ТЗ; suspended и будущие очереди
не включены. Это текущие строки общей БД, не число воркеров или lifetime totals;
одинаковые снимки разных нод нельзя суммировать. Возраст available считается от
scheduled_at по часам PostgreSQL в момент замера, не от inserted_at. При отсутствии
available возраст 0; при недоступности БД количество/возраст скрыты, availability=0.
Опрос 15с, SQL timeout 750мс без ожидания занятого пула, reader timeout 1с,
freshness <30с. Подробности — [отчёт Oban](../keep/queue1-oban-metrics-check.md).

PostgreSQL: `anime_postgres_info{version}` — константа 1 с release-версией,
`anime_postgres_version_number` — её числовое представление,
`anime_db_pending_migrations` — количество файлов текущей сборки, которых нет
в журнале БД. Опрос 15с, свежесть <30с. Пустой/потерянный каталог миграций или
отсутствующий журнал дают недоступность; файлы не исполняются, таблица не создаётся.
Поддержан текущий единый Repo с журналом schema_migrations.

`anime_db_size_bytes` — дисковый размер этой базы, не свободный диск; опрос 300с,
свежесть <315с. Для двух независимых групп есть `anime_db_metadata_available`
и `anime_db_size_available`. SQL timeout 750мс, queue=false, reader deadline 1с.
Scrape не читает SQL/файлы. Info строится из свежего числового Telemetry-замера;
Core не накапливает метки старых версий. Нет имени базы, пути миграции или DSN.
Версионный info-ряд не накапливает историю меток в Core.
[Подробности и проверки](../keep/queue1-postgres-metrics-check.md).

Активность PostgreSQL: `anime_db_active_connections`,
`anime_db_idle_in_transaction_connections`, `anime_db_oldest_transaction_age_seconds`
и `anime_db_activity_available`. Client backend текущей базы; запрос сборщика
исключён. Active включает ожидание блокировок, idle in transaction включает
aborted. Возраст — по непустому xact_start; при его отсутствии не подменяется
длительностью последнего запроса. Prepared-транзакции без соединения не учитываются.
Нужны права pg_read_all_stats; при недостаточных правах или disabled/скрытом
состоянии клиента снимок недоступен. Никаких GRANT или смены настроек при запуске.
Опрос 15с, SQL 750мс/queue=false/log=false, reader 1с, свежесть <30с. В открытой
Ecto-транзакции чтение пропускается из-за кэширования статистики. SQL на scrape
нет; старые значения не выдаются как текущие. Это не занятость пула DBConnection.
Всего теперь 56 определений Core плюс info-ряд, 57 семейств.
[Подробности и проверки](../keep/queue1-database-activity-check.md).

## Доверенные прокси и IP

На dev `TRUSTED_PROXIES` можно не задавать или оставить пустой: заголовкам не
доверяем даже от 127.0.0.1 и приватных сетей. Если действительно используется
обратный прокси, явно укажите его IPv4/IPv6 CIDR через запятую и перезапустите
приложение. Отдельный адрес задаётся с `/32` или `/128`; hostname не принимается.
Неверный список останавливает запуск с именем переменной, без её значения.
Не задавайте `0.0.0.0/0` или `::/0` вместо списка реальных прокси: это доверие всем
адресам соответствующего семейства. Приложение не включает доверие автоматически.

HTTP и подключённая LiveView используют одинаковые правила п.20 ТЗ:

- источник доверия — адрес непосредственного соединения, а не уже переписанный
  conn.remote_ip, cookie или параметры формы/подключения;
- X-Forwarded-For принимается только от доверенного адреса; все элементы проверяются,
  справа налево пропускаются доверенные узлы, выбирается первый недоверенный;
- дубли заголовка, повреждённые элементы, более 20 адресов или цепочка длиннее
  2048 байт отбрасываются целиком. Если все адреса доверенные либо заголовка нет,
  используется адрес соединения; страна unknown;
- буквальные IPv4/IPv6 разрешены, порты, zone-id, скобки и сокращённый IPv4 — нет.
  IPv4-mapped IPv6 нормализуется к IPv4, чтобы одна машина не получала два лимита;
- страна принимается только при принятой цепочке и единственном X-Geo-Country
  из двух заглавных ASCII-букв. Для будущей статистики она доступна в assigns;
  геолокации по IP и самого учёта VisitStat в этом срезе нет;
- X-Real-IP, Forwarded, True-Client-IP и CF-Connecting-IP не используются.
  Полученный IP уже применяется в существующих сессиях, аудите и лимитах;
- входящий x-request-id сохраняется только от доверенного peer, одним значением
  длиной 20–200 ASCII-символов из букв, цифр, `_`, `-`, `.`. Иначе все его значения
  удаляются и Plug.RequestId создаёт новый ID; это действует и на ранние ошибки.

Прокси обязан удалять пришедшие от недоверенного клиента служебные заголовки и
строить их заново по п.20/21. Настройка nginx/балансировщика в этом проходе не
выполнялась; она обязательна до реального развёртывания. TLS/host/proto и внешний
доступ не включены, staging/prod остаются запрещены. Отказы XFF дают безопасное
warning и событие Telemetry без адресов/содержимого заголовков; экспорт метрик
ещё не реализован. Текущий формат журналов описан ниже.

## Безопасные журналы приложения

Logger пишет плоский JSON в stdout через `Anime.LogFormatter`: время UTC с
микросекундами, уровень, фиксированное сообщение, узел, версия приложения и
request_id (null, если вне запроса). `Anime.Log.emit/2` принимает только известные
события и разрешённые типизированные поля, не произвольный текст.

HTTP-запись содержит исходный метод, шаблон маршрута, статус и длительность.
Query, токены, ник в пути, неизвестный адрес и имя отсутствующего файла не
выводятся; 404 статических ресурсов пропускается. Request_id совпадает с
заголовком ответа, включая ошибки парсера/CSRF/500. User ID допускается только
числом и только на warning/error. Пароли, cookie, email, IP, SQL-параметры,
содержимое форм и тела исключений не сериализуются. Repo настроен с log: false.

Сообщение библиотеки без нашего типа события заменяется на
`Unstructured log suppressed` с безопасным именем модуля/функции, если оно есть.
Это сознательно уменьшает диагностическую подробность: вместо добавления сырых
исключений нужно расширять перечень безопасных событий. Сторонний Logger-handler,
прямой IO/stderr и внешние системы сами по себе этой защитой не покрываются.

Проверка реального stdout без запуска приложения/БД и чтения `.env`:

```sh
MIX_ENV=test mix compile --warnings-as-errors
MIX_ENV=test mix run --no-start dev/logging_smoke.exs
```

ID ответа передаётся в подписанную сессию конкретной LiveView-страницы, а не
общую cookie; сохраняется при событиях, patch и повторном подключении. События
монтирования/параметров/форм логируются на debug, исключения — error. В журнале
только разрешённые имена view/action/event и серверный socket_id, не params.

Все нынешние воркеры используют `Anime.Worker`: new сохраняет ID постановщика
в meta.request_id. Cron создаёт собственный ID с именем воркера и временем UTC.
Во время выполнения дочерние задачи наследуют ID, повторы сохраняют его, после
завершения прежняя metadata восстанавливается. Успех/отмена/snooze — info,
повтор — warning, исчерпание/discard — error. args, результат и причина ошибки
не выводятся. Новые воркеры должны использовать wrapper; прямой perform обходит
корреляцию executor. При расширении приложения нужно дополнять allowlist логов.

Нынешние Task/start_async используют `Anime.LogContext.wrap/1`: захват ID до запуска,
восстановление прежнего контекста после callback, фиксированное сообщение ошибки
без причины/стека. Hooks handle_info/handle_async восстанавливают ID страницы.
Новые фоновые callback нужно оборачивать явно; произвольные Task не охвачены автоматически.

Отказ права из существующего AuditLog и срабатывание лимита дают warning без
личных данных. Это не замена подробного аудита и не журналирование UI-проверок
видимости кнопок. Сброс кэша прав даёт info после фактического удаления в ETS,
переносит ID через after_commit/GenServer/PubSub; при откате не записывается.
Старое сообщение кэша без ID принимается с null; значения кэша не передаются.

Swoosh-события только Anime.Mailer: принятие адаптером — debug, возвращённая ошибка
или raise/throw/exit — error. Получатели, тело/тема письма, конфигурация, результат
адаптера и исключение не попадают в JSON. У почтовой задачи сохраняется request_id;
её пропуск по истёкшему токену не считается передачей письма. SMTP не подключён.

Запуск producer очереди подтверждается его состоянием после инициализации — info;
нормальное завершение — info, аварийное — error. Используются реальный процесс
Oban и его монитор, не событие отдельной задачи. Ручной drain не имитирует старт.
После перезапуска обработчика мониторы восстанавливаются без повторного «старта».
Жизненный цикл очереди имеет request_id=null; поле oban_queue ограничено текущими
mailers/maintenance, незнакомое имя маскируется. Это не распределённый аудит и
не гарантия сохранения событий при остановке VM/обработчика; подробности в отчёте.

Dev/test теперь действительно debug. ExUnit захватывает журнал теста, не понижая
порог Logger и не отключая проверки записей. Файлы приложение не создаёт.
Безопасная проекция событий описана ниже. Затем нужны остальные служебные события (включая миграции),
rsyslog/logrotate, экран журналов и оставшаяся приёмка очереди 1.
Mix/компиляция и аварии до запуска Logger не означают гарантированный JSON-stdout
будущего релиза. Очередь 1 и production-приёмка этим срезом не закрыты.

## Безопасные события для метрик

`Anime.Metrics` под supervisor слушает framework-события и формирует новый поток
`[:anime, :metrics, ...]`. Подписчики должны использовать только `events/0` и
`contracts/0`: там описаны измерения и разрешённые метки. Framework metadata
не пересылается целиком и не становится безопасной для чужих подписчиков.

- HTTP: количество и длительность до отправки ответа, по статусу, в том числе
  ошибки парсера/CSRF и 404 статики. Router: длительность по шаблону и методу,
  число исключений по шаблону; HEAD сохраняется до нормализации Plug.Head.
- LiveView: монтирование отдельно static/connected, обработка параметров и форм,
  исключения формы по разрешённой паре view/event. Redirect при монтировании —
  отдельное подмножество, его нельзя суммировать с mount как новое монтирование.
- Oban: наблюдения stop по воркеру и exception по воркеру/виду завершения.
  Один повтор — отдельная попытка, не новая логическая задача. Stop сам по себе
  не означает бизнес-успех: он применяется также к cancel/snooze/discard.
- Отказы прав — по коду существующего разрешения, лимиты — по scope, отказы XFF —
  по фиксированной причине и транспорту. Два сработавших login/login_ip считаются
  по одному разу каждый; это число срабатываний ограничений, не уникальных запросов.
- Ecto: число операций по источнику и исходу; total/query/queue/decode/idle time,
  каждая фаза отдельно, без подмены отсутствия нулём. Источник — закрытый серверный
  контекст, не имя таблицы. Вложенные LiveView/Oban и обёрнутые async-задачи его
  восстанавливают; работа вне этих границ получает other.
- Медленные операции: total_time строго больше 500 мс, без idle_time.
  Таймауты: только типизированный queue_timeout в результате нашего Repo,
  без анализа текста и без второго учёта глобального DBConnection-события.
  Прямой Repo.checkout учитывает отказ до входа в callback отдельным безопасным
  уведомлением, без исходного исключения/opts. Ошибка внутри callback или
  вложенного запроса не добавляет второй отказ от внешнего checkout.
- Пул: три события с единственным полем value без меток — ready, waiting и
  доступность свежего снимка. Сборщик хранит только последний снимок и monotonic-время;
  обновления gauges идут через Telemetry. HTTP-отдача отсекает устаревшие значения.
- BEAM: восемь событий с value; только у памяти есть фиксированная метка kind.
  Девять категорий памяти, четыре счётчика ресурсов/GC, start/uptime и доступность —
  16 рядов. Содержимое процессов, имена атомов, PID и адреса не собираются.
- Планировщики: три события с value, замкнутые kind/id либо measurement.
  Значения и метки проверяются до публикации safe events, не только при экспорте.
  Исходные два счётчика времени не экспортируются, из них получается только доля.

Длительности событий в миллисекундах; start/uptime gauges — в секундах.
Неисправное измерение не заменяется нулём.
Динамические URL, request_id, user/socket/job ID, адреса и содержимое форм исключены.
Неизвестные метки заменяются `[unknown]`; у БД служебные операции — other,
неожиданный результат — unknown. Процесс не сохраняет наблюдения и не
заводит собственных счётчиков/ETS; во время его остановки события не переигрываются.

Агрегатор и локальная отдача Prometheus уже работают: 26 семейств count/sum и 31 gauge,
жёсткий предел 500 итоговых рядов каждого до запуска, без публикации в основном
router. Пять новых семейств БД имеют максимум 12/20/20/4/4 ряда соответственно.
Среднее время фазы считается по её собственному числу измерений, а не по общему
числу операций. Смысл, имена и PromQL — [отчёт метрик БД](../keep/queue1-database-metrics-check.md).
Прямой Anime.Repo.checkout без query-события теперь покрыт счётчиком таймаутов.
Bare DBConnection/чужие Repo и намеренно выключенные query-события вне покрытия.
Готовые соединения/ожидающие и доступность снимка реализованы, точное busy
отложено по выбору пользователя. Память/ресурсы BEAM и uptime реализованы.
Очереди и использование планировщиков, число GC реализованы; длительность GC
отложена по выбору пользователя. Версии приложения/Elixir/основного выпуска OTP
и показатели единственного реализованного кэша добавлены. Состояния задач двух
действующих очередей и возраст available добавлены. Версия PostgreSQL, размер базы
и неприменённые миграции добавлены. Серверные active/idle in transaction и возраст
самой длинной клиентской транзакции добавлены. Далее — топ-10 таблиц/индексов
по размеру и доля попаданий в буферный кеш; остальные Oban/VM, FFmpeg и инфраструктура
остаются отдельными незавершёнными пунктами.
Гистограммы/квантили и алертинг ещё не реализованы.

## Проверка ограничений существующей базы

В очереди 1 добавлены 17 CHECK: допустимые значения перечислений, границы ника и
громкости, размеры хеша/nonce токена, обязательный nonce почтового токена,
положительное окно и неотрицательный счётчик лимита. Старые миграции не изменены;
12 новых файлов сначала добавляют CHECK NOT VALID, затем валидируют отдельным шагом.

Перед обновлением существующей базы выполните read-only проверку
`priv/repo/checks/queue1_constraints.sql` через `psql -X -v ON_ERROR_STOP=1 -f …`
с явно выбранным подключением к нужной базе. Она выводит только числа нарушений,
не записи. Все 17 значений `invalid_rows` должны быть нулевыми; при ненулевых
остановитесь и разберите данные, не исправляйте и не удаляйте их автоматически.
После проверки примените `mix ecto.migrate` с тем же окружением базы.

Подробности SQL-тестов, отката только новых миграций и границы гарантии:
[проверка ограничений БД](../keep/queue1-db-constraints-check.md).

## Локальные тестовые аккаунты

По отдельному запросу созданы `demo_owner`, `demo_admin`, `demo_moderator`, `demo_editor`
и `demo_user` с соответствующими системными ролями. Email вида `<ник>@anime.test`
подтверждён сразу, внешняя почта не отправляется. Вход принимает ник или email.
Владелец при первом входе должен сменить временный пароль.
Разные случайные пароли выданы в ответе пользователю, в исходниках они не сохраняются.

Для повторного создания отсутствующих аккаунтов после загрузки dev-переменных:

```sh
mix run priv/repo/demo_accounts.exs
```

Скрипт разрешён только в `MIX_ENV=dev`, `APP_ENV=dev`, для изолированной базы
`anime_dev` на `127.0.0.1:59432` и локального почтового адаптера. Существующие аккаунты,
пароли и матрица не меняются; занятые логины/email пропускаются. Если уже есть активный
owner, второй тестовый владелец не создаётся. Это не часть обычного seed/развёртывания;
тестовые аккаунты нельзя переносить в production.

## Что можно открыть

Изолированный UI-стенд с новой временной БД и синтетическими данными:
`bash dev/check_queue1_browser.sh`. HTTP `localhost:4002`, PostgreSQL только
loopback 59434, существующие базы и `.env` не используются. Скрипт запускает
`dev/admin_ui_smoke.exs`; остановка своей VM через `System.stop()` в IEx также
останавливает временную БД, оставляя данные/логи. Ограничения и свежие результаты —
[браузерная приёмка](../keep/queue1-browser-acceptance.md).
Предыдущая проверка таблиц —
[отчёт UI-проверки](../keep/queue1-admin-visual-check.md#среда-и-воспроизведение).
Не направляйте его на dev/рабочую базу и не публикуйте наружу.

Наборы прав для меню и кнопок кешируются в ETS по роли. При изменении матрицы/ролей
кэш сбрасывается после commit; серверные проверки доступа по-прежнему читают БД.
Падение владельца кэша не выдаёт доступ: чтение переключается на БД, владелец
перезапускается с пустой таблицей. Остальные кэши и экран их управления ещё не реализованы.
Подробности: [кэш прав](../keep/queue1-permission-cache-check.md).

- `/register`, `/login`, `/confirm/:token`, `/password/reset`, `/password/reset/:token`;
- `/profile`, `/profile/settings`, `/password/change` — после входа;
- в настройках — смена ника, ожидание подтверждения email и запрос удаления;
- `/u/:nick` — публичный профиль: ник, дата регистрации и разрешённый значок роли;
  email, IP, сессии и история просмотра не выдаются даже при просмотре сотрудником;
- список сессий показывает текущую, даты создания/активности, IP и User-Agent;
  «Завершить все, кроме текущей» сохраняет текущий вход и отзывает также все remember-me;
- избранное, оценки, комментарии и жалобы в публичном профиле пока заглушки очереди 4,
  аватар пока инициал. Переключатель приватности уже меняет публичное представление;
- `/account/restore/:token` — отмена удаления в течение 30 суток, затем новый вход;
- `/admin/users`, `/admin/users/blocked` — поиск, фильтры, сортировка и страницы по 50;
- в реестре блокировок — причина, начало, окончание и оператор; фильтры по сроку,
  оператору и датам именно блокировки (UTC), включая записи без указанного оператора;
- вкладка блокировок в карточке хранит историю по 50 событий с причинами и сроками;
  она не исчезает после разблокировки, автоматическое снятие срока подписано отдельно;
- статус пользователей расположен перед действиями; карточка показывает статус/роль,
  заглушку аватара и ссылку на публичный профиль. Активные сессии выбираются по 50 отдельно
  от обзора, без почтовых токенов и секретов; страницы сохраняют пользователя и вкладку.
  Отзыв строки требует подтверждения, «Завершить все сессии» действует на все страницы.
  Таблицы сессий/блокировок содержат ID и прокручиваются внутри ограниченного контейнера;
- чекбоксы выбирают только текущую страницу, смена фильтра/страницы/сортировки снимает выбор;
  доступны массовая смена роли и завершение сессий, не более 50 аккаунтов, с подтверждением.
  Отказ по одному аккаунту не отменяет остальные действия. Сводка показывает причины;
  изменённые другим оператором записи не перезаписываются и остаются выделенными;
- действия строки: открытие карточки, смена роли, переход к блокировке в карточке;
  массовая блокировка и массовое удаление не предусмотрены;
- `/admin/users/:id` — обзор, блокировки, сессии и активность: смена роли, блокировка/разблокировка,
  отзыв сессий с подтверждением и проверкой прав. Собственные административные действия
  и действия над более привилегированным пользователем запрещены;
- истёкшие блокировки снимаются каждые 15 минут, письмо восстановления доступа видно
  в локальном почтовом ящике. Оценки и будущие таблицы этим срезом не обрабатываются;
- в карточке доступны правка ника/email/locale, запрос удаления с точным ником и отмена;
  устаревшая форма не перезаписывает изменения. Смена email снимает подтверждение и
  отзывает старые сессии/почтовые ссылки. Удаление имеет отсрочку 30 суток; операторский
  запрос не отправляет ссылку восстановления, отмена не возвращает старые токены;
- `/admin/users/activity` — история с отдельным правом, фильтрами и пагинацией по 50;
  фильтр пользователя означает автора действия. Прежние/новые значения полей не выводятся.
  Теперь учитываются лимиты входа, выход, запрос восстановления, смена пароля с IP,
  смена языка и приватности избранного. Гостевой запрос восстановления не приписывается
  владельцу введённого email; одинаковое поведение для неизвестного/заблокированного адреса.
  Повторный выход/сохранение без изменений не дублируют событие. Пароли и токены не пишутся.
  События ещё не реализованных аватара/уведомлений/согласия/возраста/выгрузки остаются впереди;
- `/admin` — переход на первый доступный экран. Общая навигация показывает только
  разрешённые разделы; `/admin/dashboard` пока показывает состояние доступа без метрик.
  Есть переключение языка с сохранением текущего экрана/черновика, тема, профиль и выход;
  предусмотрены компактная планшетная панель и мобильное меню;
- списки сохраняют фильтры, сортировку и страницу в URL; чип снимает отдельный фильтр,
  пагинация содержит первую/предыдущую/номера/следующую/последнюю страницу;
- основные списки асинхронно обновляются после фильтрации/сортировки/перехода страницы:
  скелетоны до 10 строк, сохранение высоты, блокировка действий до завершения запроса.
  Новый запрос отменяет старый, запоздавший результат не применяется. Ошибка или таймаут
  показывают кнопку повтора, а не пустой список. Доступ проверяется заново перед показом.
  Начальная отрисовка, карточка пользователя и матрица остаются синхронными;
- сортируемые заголовки имеют стрелки и aria-sort. Клик новой колонки включает DESC,
  повторный — ASC; страница и массовое выделение сбрасываются, фильтры остаются.
  Одинаковые значения разделяются ID. В ролях, разрешениях и активности виден ID;
  неиндексированные названия/счётчики не изображают работающую сортировку;
- `/admin/roles` — роли: создание, код/название/значок, роль новых регистраций, удаление
  незанятой несистемной роли. Системные коды и owner защищены;
- `/admin/roles/permissions` — справочник 99 разрешений только для чтения;
  оба списка фильтруются и разбиваются на порции по 50 на стороне PostgreSQL;
- существующие административные списки различают отсутствие данных и отсутствие
  совпадений; «Сбросить фильтры» сохраняет область карточки пользователя. Шапка,
  фильтры и пагинация остаются на месте, счётчик находится рядом с заголовком;
  таблицы прокручиваются внутри области до 65vh, шапка и первая колонка закреплены.
  Действия ролей — подписанные для скринридера иконки с подсказками. «Создать роль»
  переводит к пустой форме и не пишет запись до её сохранения;
- `/admin/roles/matrix` — изменение матрицы с просмотром разницы и подтверждением;
  все изменённые роли сохраняются одной транзакцией, устаревшая форма не перезаписывает БД;
- поиск/область/роль матрицы сохраняются в URL (`q`, `group`, `role`); чипы и «Сбросить»
  меняют только фильтры. Patch и смена языка сохраняют черновик в открытой странице,
  но полная перезагрузка его теряет; сами права в URL не записываются;
- даты админки имеют форматы RU/EN и точную UTC-подсказку; язык не меняет часовой пояс.
  Счётчики разделяют тысячи по локали, ID/коды/URL остаются неизменными;
- описания 99 разрешений, названия областей и исходные системные роли переведены RU/EN;
  поиск понимает оба языка. Собственные названия ролей сохраняются дословно; в форме
  правки показано хранимое имя. Коды прав/ролей и действия журнала не переводятся;
- сообщения об отказе объясняют причину и следующий шаг без технического кода;
  смена языка переводит текущий отказ и сохраняет несохранённые значения формы;
- системный admin читает роли/справочник; изменять их и матрицу по исходным правам может
  owner. Локальные тестовые аккаунты описаны выше; обычный seed не создаёт их;
- те же публичные адреса с `/en` — английский интерфейс;
- язык явно открытой страницы задаёт её URL: `/catalog` — RU, `/en/catalog` — EN.
  При входе через `/` приоритеты: профиль → cookie → язык браузера → RU; английский
  выбор даёт 302 на `/en` с прежними query-параметрами. Админка использует язык профиля;
- переключатель RU/EN возвращает на ту же страницу с её фильтрами, в том числе после
  LiveView patch; у пользователя сохраняется поле профиля, у гостя — cookie на 365 суток.
  Регистрация запоминает язык формы. На обязательной смене пароля переключение языка
  доступно, но не снимает запрет доступа к другим страницам. 403 переведена на RU/EN;
- `/`, `/catalog`, `/genres`, `/blog` и прочие будущие разделы — **явные заглушки**;
- неизвестные адреса и отсутствующие публичные профили — настоящая HTTP 404 с шапкой,
  футером, ссылками на главную/каталог и noindex,follow. Поиск появится в очереди 3;
- 500 — независимый от базы экран без стека/SQL/параметров, с номером запроса;
  тесты проверяют его через обработчик Phoenix, не через публичный маршрут падения;
- `/healthz` — процесс отвечает; `/readyz` — БД, миграции и MinIO доступны.

Без запущенного MinIO корректен ответ `/readyz` **503 с `failed: ["storage"]`**.
Это не означает, что хранилище уже настроено: его установка и создание бакетов не выполнены.
`APP_ENV=staging/prod` намеренно запрещён до завершения требований безопасности и эксплуатации.

## Проверка

Тестовая база определяется `TEST_DATABASE_URL`; имя должно отличаться от базы разработки.
Тесты создают/мигрируют её, используют SQL Sandbox и не отправляют внешние письма.
Шестнадцать конкурентных тестов требуют имени с суффиксом `_test`, используют отдельные соединения
с коммитами и очищают только созданные ими записи. Их нельзя направлять на общую рабочую БД.

```sh
mix format --check-formatted
mix compile --warnings-as-errors
MIX_ENV=test mix test --warnings-as-errors
mix security.check
mix assets.build
node test/js/admin_table_test.mjs
node test/js/admin_shell_test.mjs
node test/js/public_header_test.mjs
```

`mix security.check` запускает оба аудитора зависимостей и Sobelow, останавливаясь
на ошибке. `deps.audit` не заменяет `hex.audit`: их источники предупреждений различаются.
Если Hex сообщил об использовании кэша, перед релизом повторите проверку при доступном
реестре. Успешные тесты не заменяют аудит. CI пока не подключён.

Sobelow 0.15.0 сейчас возвращает **0 замечаний**, exit 0, без исключений и подавления.
Router объявляет CSP с функцией чтения готовой политики Endpoint; адаптер передаёт
её Phoenix без второго nonce и без статической ослабленной замены. Девять тестов
проверяют полный заголовок, его единственность, свежесть nonce, ошибки и границы доверия.
Это не завершение безопасности сайта: будущие видео/интеграции, эксплуатация,
полный браузерный прогон и CI остаются в IMPLEMENTATION.md.
